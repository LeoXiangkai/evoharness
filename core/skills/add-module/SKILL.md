# /add-module — 一键新增业务模块（Agent 协作版）

> 使用 PM→SA→Dev→QA→PM 验收多 Agent 协作流程，
> 从需求分析到全套可运行代码一步到位，产物持久化到任务文件夹。
>
> **用法：** `/add-module {模块名或需求描述}`
> **示例：** `/add-module 用户管理` 或 `/add-module 新增一个通知公告模块，支持增删改查和分页查询`

---

## 前置准备

在执行任何步骤之前，先检查：

1. 当前项目根目录是否存在 `.claude/` 目录 — 如果不存在，提示用户先执行 `/setup-ai-coding`（若已安装）初始化项目档案
2. 从 `CLAUDE.md` 中读取项目的技术栈、命名规范、模块结构等信息
3. 解析用户输入的模块名/需求描述
4. **创建任务文件夹**：`.claude/tasks/<YYYYMMDD>-<任务简述>/`

---

## Step 1：PM 需求分析 + 需求冻结（门1）

**调用 PM Agent**，传入以下 prompt：

```
分析以下新模块需求，输出执行计划与需求冻结产物：

需求：{用户输入的模块名/需求描述}

请输出：
1. 需求理解（一句话概括）
2. 需求规模判定（大需求/小需求，判定依据见下）
3. 澄清点（如有歧义列出问题）
4. 覆盖矩阵（需求冻结门1，必产）：逐条把需求点映射到
   `需求点 → 实现位置(模块/文件) → 验收方式(unit/contract/integration/e2e/manual)`
   有需求点落不到任何实现 = 漏需求，必须补。
5. 可判定验收条件（EARS 前置筛）：每个行为单元改写成
   `WHEN/IF/WHILE <可观测条件> THE SYSTEM SHALL <可观测输出>`
   写得出 SHALL 句 = 可机器判定；写不出 = 当场判 manual 并记原因，别配假断言。
6. 执行计划（Step 分解，每个 Step 标注 @next-agent）

需求规模判据（大/小）：
- 大需求：涉及新表 / 新增对外接口 / 跨模块 → 走完整验收门（Step 7）
- 小需求：单模块内、无新表无新对外接口 → 可省 PM 验收，但 e2e 沉淀（Step 6.5）不省

注意：
- 使用 Read/Grep 工具读取 CLAUDE.md 了解项目规范
- 需求冻结的完整标准见 Skill `sdd-pipeline` 门1
- 输出写入任务文件夹：01-requirements.md
```

**等待 PM Agent 返回分析结果，写入 `01-requirements.md`。**

> 需求冻结（覆盖矩阵 + EARS 可判定验收条件）是本模块"需求一致性"的基线，
> 后续 Step 7 验收要回链它。标准见 `sdd-pipeline` 门1。

---

## Step 2：用户确认需求

将 PM 输出的需求分析展示给用户，优先使用选项式确认；若当前环境不支持，就用简短问题确认：

- 需求理解是否准确
- 是否有补充或修改
- 是否继续执行

**用户确认后才进入下一步，不要自动跳过。**

如果用户要求修改，将修改意见传回 PM Agent 重新分析，直到用户满意。

---

## Step 3：SA 架构设计

**调用 SA Agent**，传入以下 prompt：

```
根据以下已确认的需求，设计新模块架构方案：

需求：{用户输入的模块名/需求描述}
PM 计划：{Step 1 PM 输出的执行计划}

请输出：
1. 模块命名和归属（模块目录名、中文说明）
2. 数据库表结构 DDL（表名、字段、索引、关联关系）
3. API 接口清单（路径、方法、请求/响应体）
4. 待开发文件清单（含完整路径，表格格式）
5. 与现有模块的关联关系（如有）

注意：
- 读取 CLAUDE.md 获取项目规范（命名约定、包路径等）
- 如需宏观代码结构分析，自行使用 Read/Grep 工具
- 输出写入任务文件夹：02-design.md
- 完成后标注 @next-agent: dev
```

**等待 SA Agent 返回设计方案，写入 `02-design.md`。**

---

## Step 4：用户确认方案

将 SA 输出的设计方案展示给用户，优先使用选项式确认；若当前环境不支持，就用简短问题确认：

- 表结构是否需要调整（增减字段、修改类型）
- API 接口是否需要调整（增减接口、修改路径）
- 是否有其他补充需求

**用户确认后才进入下一步，不要自动跳过。**

如果用户要求修改，将修改意见传回 SA Agent 重新设计，直到用户满意。

---

## Step 5：Dev 代码生成

新模块属 C 档，编码交**外部执行体**（高档模型，`rules/executor-handoff.md §规则 1`）；外部执行体不可用时降级为中档模型 `dev` 子代理，标明"因外部执行体不可用降级"。主会话不直编。

派工前确认：已在 worktree 内（`rules/worktree-management.md`），Step 3 方案与 Step 4 用户确认结论已冻结。外部执行体以后台任务启动，工作目录指向 worktree 绝对路径。

prompt 按 `rules/executor-handoff.md §派工方式（硬约束）` 的「prompt 必带」组织，至少包含：

```
目标：根据已确认的架构方案，生成全套业务代码。
worktree：{绝对路径}
已冻结方案：{Step 3 SA 输出的完整方案}
待开发文件清单：{SA 输出的文件清单表格}；只改清单内文件 + 必要的模块注册，禁改其他模块
生成：Entity、请求/响应 VO、Mapper 接口、Mapper XML、Service 接口与实现、Controller；DDL / 数据脚本只生成文件，不执行
风格：读项目 CLAUDE.md 的命名规范与代码模板，抽样一个已有模块对齐风格
验证：项目构建命令（如 mvn compile -pl <模块> -am）；相关单测（如 mvn test -pl <模块> -am）
返回：实际改动文件、逐项执行结果、命令与退出码、DDL 文件路径、已知风险
不得再派子代理、不得调用代码审查 skill
{rules/executor-handoff.md §规则 2 边界清单}
```

执行体回调后，主会话：

1. diff 自审，并按 `rules/executor-handoff.md §执行体汇报必独立核实` 独立跑一次编译
2. **DDL / 数据脚本自行执行**：用项目约定的数据库执行工具执行到开发与测试环境并确认"已应用"（生产除外）
3. 同步更新项目 CLAUDE.md 的业务模块清单（Read→修改→Write）
4. 写入变更日志到任务文件夹：`03-code-change.md`（含 DDL 执行回执与核实结论），进入 Step 6

---

## Step 6：QA 测试验证（门3 QA 证据）

**调用 QA Agent**，传入以下 prompt：

```
为刚生成的 {模块名} 模块编写测试用例并执行验证。

测试依据：
- 变更日志：任务文件夹/03-code-change.md
- 被测代码：{Dev 输出的被测代码清单}
- 需求冻结：任务文件夹/01-requirements.md 的覆盖矩阵与验收条件

请：
1. 按 `refs/design-doc-principles.md §四` 测试归属表落地（unit/contract/integration/e2e/manual），
   归属层必须真实可核——声明 contract 就要有 @WebMvcTest，不许归属画饼。
2. 为 Service 层编写单元测试（Mock 数据访问层）
3. 为 Controller 层编写契约/集成测试
4. 执行测试并留证据（门3 QA 证据，标准见 sdd-pipeline）：
   - 每条用例留执行时间、实际结果、关键日志/请求响应——PASS 也要留，不靠代码逻辑推断 PASS
   - FAIL 先判代码错还是用例错，判据写进报告；说不清默认按代码错
   - 禁止放宽断言 / 删测试 / -DskipTests 把红改绿
5. 覆盖矩阵回链：验证每个需求点的验收方式是否真实跑过
6. 需求规模判定（大需求/小需求）
7. 写入测试报告到任务文件夹：04-test.md
8. 根据需求规模判定：
   - 大需求 → @next-agent: pm（触发验收）
   - 小需求 → 主会话收口，做审查判档

注意：
- 读取 CLAUDE.md 获取测试框架信息
- 抽样已有测试文件确认测试风格
- 如果项目无法运行测试，说明原因并标 Not-tested，不得写成通过
```

**等待 QA Agent 完成测试，写入 `04-test.md`。**

---

## Step 6.5：e2e 回归沉淀（验证未收口的唯一标准）

**用例跑过但没沉淀，视为验证未收口。** 资产是给**后续功能回归**用的，不能简化。

1. **唯一落点**：脚本统一落项目声明的 e2e 资产宿主（项目「测试基础设施映射」中声明；未声明时先与用户确定并写回声明），不落 `/tmp`；
   框架如 Playwright（独立工程 + 锁版本 + README 写装依赖/登录取态）。
2. **覆盖度：主要 + 次要流程都覆盖**——按 02-design 测试归属表的 e2e 行，把本模块**主流程 +
   次要/异常分支**都落成可执行 spec，不是只跑黄金路径 3-5 条的简化版。覆盖少了，后续回归拦不住。
3. **登记资产索引**：登记到项目资产索引，必须给 **entrypoint 一行可复制命令**
   （形如 `cd <workspace> && npx playwright test e2e/<模块>.spec.ts`）。
4. **检索可发现**：按业务关键词能从资产索引搜到本模块资产。
5. **手搓第 2 次必升公共件**：登录/取数/造数等重复步骤升为表一公共件。

> 标准见 `sdd-pipeline` e2e 回归沉淀 与 `refs/test-suite-hygiene.md §四点一 / §四点二`。
> 小需求可省 Step 7 的 PM 验收，但本步 e2e 沉淀**不省**。

---

## Step 7：PM 验收（门4 验收判据，大需求触发）

**根据 QA 的需求规模判定结果决定是否执行：**

### 大需求（自动触发）

验收是**机器判**，不是"PM 看一下"。四项判据缺一不过（标准见 `sdd-pipeline` 门4）：

| # | 判据 | 证据 |
|---|------|------|
| 1 | 需求全覆盖：01-requirements 覆盖矩阵无空格，每需求点有实现+测试 | 覆盖矩阵 |
| 2 | QA 证据齐：04-test 证据链完整，无"看代码推断"的 PASS | 测试报告 |
| 3 | e2e 已沉淀：核心流程 e2e 脚本已固化并登记资产索引 | 资产索引命中 |
| 4 | 审查判档完成：主会话 diff 自审 + 独立 reviewer 按 `code-review` skill（若已安装）风险门控判 skip/single/dual，未安装时主会话按 diff 风险自行判定 | 自审结论 + 判档结论 |

**调用 PM Agent**，传入以下 prompt：

```
对已完成的 {模块名} 模块按门4 四项判据进行功能验收（标准见 sdd-pipeline）。

验收依据：
- 需求冻结：任务文件夹/01-requirements.md（覆盖矩阵 + 验收条件）
- 设计方案：任务文件夹/02-design.md
- 变更日志：任务文件夹/03-code-change.md
- 测试结果：任务文件夹/04-test.md（QA 证据链）
- e2e 资产：资产索引中本模块登记项

逐项核对门4 判据：
1. 需求全覆盖：覆盖矩阵每个需求点是否都有实现+测试，无空格
2. QA 证据齐：PASS 用例是否都留了证据，无推断式 PASS
3. e2e 已沉淀：核心流程 e2e 脚本是否已登记资产索引、给 entrypoint
4. 接口契约：API 路径、方法、响应结构是否与 02-design 一致
5. 文档同步：项目 CLAUDE.md 业务模块清单是否更新

验收结论：
- 四项判据全过 → 主会话收口，做审查判档
- 任一判据不过 → @next-agent: dev（列出缺口，按判据补）

写入验收报告到任务文件夹：05-acceptance.md
```

**等待 PM Agent 完成验收，写入 `05-acceptance.md`。**

### 小需求（跳过 PM 验收）

小需求省 PM 验收，但 **e2e 沉淀（Step 6.5）与审查判档不省**，直接进入 Step 8。

## 异常处理

- **任何一步 Agent 返回错误**：停止流程，向用户报告错误原因和已完成的步骤
- **用户在 Step 2 或 Step 4 取消**：终止流程，保留已生成的任务文档
- **文件冲突**：如果目标目录/文件已存在，询问用户是覆盖还是终止
- **测试失败**：分析原因，区分测试代码问题还是业务代码 bug，返回 Dev 修复。**返工输入契约必带六项以 `sdd-pipeline §返工契约` 为唯一权威**（失败事实原文 / 证据路径 / 最小复现 / 已排除的假设 / 禁改范围 / 根因反向证伪判据）；禁改范围恒含"不许改断言、不许删测试、不许 `-DskipTests`"。多个发现一次性批处理返工，不改一个看一个。

  Dev 修完**必回 Step 6 重跑该模块全部测试**，不是只跑失败那一条——只跑失败项发现不了返工引入的回归。
  交外部执行体修时走 `rules/executor-handoff.md`；子代理接管时同契约适用。

## 任务文件夹结构

```
<项目根目录>/.claude/tasks/<YYYYMMDD>-<任务简述>/
├── 01-requirements.md  # PM 需求分析 + 需求冻结（覆盖矩阵 + EARS 验收条件）
├── 02-design.md        # SA 架构设计方案
├── 03-code-change.md   # Dev 变更日志（含 DDL 执行回执）
├── 04-test.md          # QA 测试报告（含证据链）
└── 05-acceptance.md    # PM 验收报告（大需求，按门4 四项判据）
```

e2e 脚本不在这里——落项目 e2e 资产宿主并登记资产索引（见 Step 6.5）。

## 质量门（与 auto-sdd 共享，单一事实源在 sdd-pipeline）

本 skill 是**有人驾驶**模式（Step 2/4 用户确认），质量门与 auto-sdd **完全相同**：
门1 需求冻结（Step 1）/ 门3 QA 证据（Step 6）/ 门4 验收判据（Step 7）/ e2e 回归沉淀（Step 6.5）。
门的详细标准统一见 Skill `sdd-pipeline`，本文件不重复。
