# sdd-pipeline —— SDD 共享质量骨架

> 目标：保证**需求一致性**与**代码高质量**，并把 e2e 验证**沉淀成可回归资产**。
> 本骨架是被引用的单一事实源，不是一个可自然语言触发的能力。

## 质量脊柱（两个入口 skill 共用，门完全相同）

```
需求 → [门1 需求冻结] → 开发 → [门2 设计/编码] → 测试 → [门3 QA证据] →
验收 → [门4 验收判据] → [e2e回归沉淀:脚本固化+登记+可检索]
```

四道门全部**机器可判**，不是"Agent 看一下"。过不了门不进入下一阶段。

---

## 门1 · 需求冻结（进开发前必过）

治"需求一致性"——把"用户想要什么"冻结成可判定、可溯源的契约，防理解与实现同源地错。

1. **覆盖矩阵**：逐条把需求点映射到 `需求点 → 实现位置(goal/文件) → 验收方式(测试层)`。
   **有需求点落不到任何实现 = 漏需求**，补实现再过门。
2. **可判定验收条件（EARS 前置筛）**：每个行为单元改写成
   `WHEN/IF/WHILE <可观测条件> THE SYSTEM SHALL <可观测输出>`。
   - 写得出 SHALL 句 = 可机器判定 → 进 unit/contract/integration/e2e；
   - **写不出 = 当场判 `manual` 并记原因**，别勉强配假断言（false-confidence 温床）。
3. 需求**模糊 / 口径不明 / 自相矛盾** → 不进开发，先澄清（若已安装需求澄清类 skill 用它，否则主会话列问题问用户）。

---

## 门2 · 设计/编码（进测试前必过）

治"实现偏离契约"——开发收口时确认契约已冻结、改动经过自审。

1. **契约已冻结**：对外接口、字段、SQL 与数据口径在编码前已确定并落在设计或需求产物里；编码中发现需要改契约 → 回到设计更新产物，再继续。
2. **diff 自审有结论**：逐项过逻辑正确、副作用（事务/缓存/锁/线程）、异常路径、周边集成、夹带（每行改动可追溯到本次需求）；结论写进汇报，编译通过不等于审查通过。

两项缺一不过。证据：自审结论。

---

## 门3 · QA 证据（测试收口必过）

治"代码高质量"——没有测试人员时的可信度保障，PASS 也要能拿出证据。

1. **每条用例留证据**：执行时间、实际结果、关键截图/日志/请求响应——**PASS 也要留**，
   不能靠代码逻辑推断 PASS；证据不足只能标 BLOCKED。
2. **测试归属按 `refs/design-doc-principles.md §四`**（行为单元 + 5 维打分）落地，
   归属层（unit/contract/integration/e2e/manual）必须真实可核：
   声明了 contract 却 0 个 `@WebMvcTest` = 归属画饼（`refs/test-suite-hygiene.md §八.6`）。
3. **FAIL 先判代码错还是用例错**，判据写进报告；说不清默认按代码错处理。
   禁止靠放宽断言 / 删测试 / `-DskipTests` 把红改绿（`refs/test-suite-hygiene.md §九`）。
4. **DDL / 数据脚本自行执行**：用项目约定的数据库执行工具执行到开发与测试环境并确认"已应用"（生产除外），
   不只生成文件让用户手动跑（`rules/executor-handoff.md §主会话硬门禁`）。

---

## 门4 · 验收判据（验收收口必过，四项缺一不过）

把"验收"从可选改成机器判。四项全部满足才算验收通过：

| # | 判据 | 证据 |
|---|------|------|
| 1 | **需求全覆盖**：门1 覆盖矩阵无空格，每个需求点都有实现+测试 | 覆盖矩阵 |
| 2 | **QA 证据齐**：门3 证据链完整，无"看代码觉得没问题"的 PASS | 测试报告 |
| 3 | **e2e 已沉淀**：核心流程 e2e 脚本已固化并登记（见下"e2e 回归沉淀"） | 资产索引命中 |
| 4 | **审查判档完成**：主会话 diff 自审必做；独立 reviewer 是否派由 `code-review` skill（若已安装）按风险门控决定 skip/single/dual，未安装时主会话按 diff 风险自行判定 | 自审结论 + 判档结论 |

## e2e 回归沉淀（验证未收口的唯一标准）

治"e2e 一次性"——**用例跑过但没沉淀，视为验证未收口**。资产是给**后续功能回归**用的，
不是当次验证的一次性耗材，所以**不能简化**。

1. **唯一落点**：e2e 脚本统一落项目声明的 **e2e 资产宿主**（写在项目「测试基础设施映射」里；
   未声明时先与用户确定并写回声明），不落 `/tmp`，不在两处各存一份可运行副本。
2. **覆盖度：主要 + 次要流程都覆盖**，不能只跑黄金路径那种简化版。
   按 `refs/design-doc-principles.md §四` 测试归属表的 e2e 行，把该功能的**主流程 +
   次要/异常分支**都落成可执行 spec——它是后续回归的拦截网，覆盖少了回归就拦不住。
3. **框架与工程自包含**：宿主是独立可运行工程（如 Playwright：`@playwright/test` 锁版本 +
   锁文件 + `README.md` 写装依赖与登录取态），UI 用浏览器、API 用 request context。
   entrypoint 形如 `cd <workspace> && npx playwright test e2e/<模块>.spec.ts`。
4. **登记资产索引**：落盘 + 在项目资产索引登记（含 entrypoint），
   两步都做完才算交付（`refs/test-suite-hygiene.md §四点一`）。
5. **检索可发现**：按业务关键词能从索引搜到；动手做测试前必须先查索引
   （`refs/test-suite-hygiene.md §四点二`）。
6. **手搓第 2 次必升公共件**：登录/取数/造数等重复步骤（批次里出现 `/tmp/*.mjs`、
   临时 curl、重复会话重建）升为宿主内的公共件。

> 落点目录结构示例：
> ```
> <e2e 资产宿主>/
> ├── e2e/               # spec 文件（主要+次要流程）
> ├── playwright.config.ts
> ├── package.json       # @playwright/test 锁版本
> ├── <锁文件>
> └── README.md          # 装依赖 + 登录取态
> ```

## 返工契约

测试失败 / 审查发现问题交执行方修复时，返工输入**必带六项**，缺任一不得派工：

1. **失败事实**：用例/测试 ID + 完整 actual vs expected 原文，不转述；actual 是不含异常信息的兜底文案时必须附真实堆栈或异常类名
2. **证据路径**：evidence 文件、日志行号、DB 查询与结果
3. **最小复现**：可直接执行的命令或步骤
4. **已排除的假设**："已验过不是 X、不是 Y，依据是 Z"
5. **禁改范围**：不许动断言 / 测试预期 / 用配置绕过；不许扩大改动面
6. **根因判据**：能反向证伪——恢复旧实现，该测试应重新失败

多个发现一次性批处理返工，不"改一个看一个"（`rules/executor-handoff.md §规则 3`）。
