# 需求渐进式入口

## 职责与边界

接收一句话、聊天记录、会议纪要或截图描述，不要求用户先写 PRD。只补齐可执行需求，不写设计、不拆任务、不写代码。

## 流程

1. 先判输入成熟度：
   - **L0**：一句话或想法，缺目标、范围或验收。
   - **L1**：有目标但缺验收或范围。
   - **L2**：目标、范围、验收均近完整，直接进入交接。
2. 先查仓库代码和已有文档；能推出的默认值先采用并标明依据，不问用户能被仓库回答的问题。
   **读代码是浅读**：只定位入口方法和同类做法，约 3~5 轮就停。超过说明复杂度判低了，按交接表升级 `req-analysis`，不在本 skill 内继续深挖。
   **红线上浮**：命中改已有契约 / PII / 权限 / 跨模块 / 跨进程 / 新对外接口 / 新表字段 / 状态机>3 任一信号，直接按 T2 以上处理，行数少不作豁免。发现读到的代码与需求明显冲突，只标注，不在本 skill 内展开核查。
3. 按成熟度决定提问方式：
   - **L0**：先走 `grilling` 追问目标、非目标、验收，再压成需求卡或简报。
   - **L1**：仍一次用 `AskUserQuestion` 批量提问，最多 5 题，使用选项式问题，不逐题往返；批量题后仍有阻塞歧义则升级 `grilling`。
   - **L2**：不问，直接进入交接。
   批量题只问：目标与价值、非目标、验收（可观察结果）、影响范围（模块/接口/表/角色）、约束（权限/数据/兼容/发布）。
   `grilling` 是可选增强，不是硬依赖：未安装时降级为直接问答，并在输出中说明缺口。
   隐性需求四问（需求里常不写、线上易出事；**各成熟度都过，含 L2**，先从仓库推，推不出的写 `<待确认>`，不适用写"不涉及"，不占批量题的 5 题名额）：
   - 幂等性：重复提交、重试、MQ 重复消费时，结果是否一致
   - 一致性：主从延迟、缓存与库、跨服务/跨表写入失败时数据是否会错位
   - 兼容性：存量数据、老版本客户端、灰度期新旧并存是否受影响
   - 可观测性：出问题时靠什么定位（关键日志、埋点、审计、告警）
4. 不得编造字段、接口或数字；缺失写 `<待确认>`，未确认内容不得当作已确认。落盘前先展示草稿。

## 产出分档

- **需求卡**：单页、单接口或单规则。对话直接输出 ≤15 行，含目标、非目标、验收（Given-When-Then 或 `WHEN ... THE SYSTEM SHALL ...`）、影响范围、代码入口（浅读已定位的 `file:line`，没读到写"未定位"）、隐性需求四问（一行）、待确认；按需落 `.ai-coding-java/artifacts/<work-id>/requirement-brief.md`。涉及多端或状态字段时，在卡里各加一行（各端做什么 / 状态转换）。
- **需求简报**：新模块、跨模块或涉及接口/表变更。按下列小节输出，按需落 `.ai-coding-java/artifacts/<work-id>/requirement-brief.md`：
  - 目标与非目标
  - 角色与权限
  - 流程：触发条件、前置条件、输入边界、正向流程、异常处理
  - 状态转换（涉及状态字段时列出状态与转换条件，不涉及写"不涉及"）
  - 多端展现：web / h5 / admin 逐端写清各端做什么，不涉及的端写"不涉及"
  - 验收（Given-When-Then 或 `WHEN ... THE SYSTEM SHALL ...`）
  - 数据边界与已知直接模块：只列已知项；相关模块、数据依赖的三级分级由 `req-analysis` 负责，不在此展开
  - 代码入口：浅读已定位的 `file:line`（Controller / Service / Mapper / 同类做法），供 `req-analysis` 直接承接
  - 隐性需求四问
  - 待确认
- **PRD 入口**：多个 Story、Epic 或 Bundle，转 `prd` skill，不在本 skill 内拆 Story。

## 交接建议

| 产物 | 下一步 skill |
|---|---|
| 验收可判定且完整 | `auto-sdd` |
| 新模块需逐步确认 | `add-module` |
| 小改 | 直接 worktree 开发（T0/T1） |
| 仍有阻塞歧义 | 升级 `grilling` 追问；未安装则降级为直接问答并在输出中说明缺口 |
| 命中上文红线，判为 T2 及以上 | `req-analysis`（以当前代码为依据查缺项、冲突、影响面） |

**转 `req-analysis` 时不停顿**：这是同一条需求流水线的内部衔接，不是用户决策点。判到 T2 及以上后，需求卡里只用一句话标注判档依据（命中哪条红线），随即在同一轮直接调用 `req-analysis` 继续，不写"下一步 / 我现在就开始"之类的预告，不等用户确认。只有 `req-analysis` 自身遇到需用户拍板的口径问题，才在其内部提问。
