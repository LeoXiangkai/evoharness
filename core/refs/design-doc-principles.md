# 方案文档产出规则

适用于任何 SDD 任务中的 `01-requirements.md` / `02-design.md` / `docs/plans/*` 类文档。


## 一、只写策略与契约，不写完整实现

**保留**（是契约/约束，实现方 必须遵守）：

- DDL 字段/索引（含"字段严格同 X 表"这类对齐来源）
- 接口契约（URL、参数、返回结构、状态码）
- 状态机（枚举 + 转移）
- SQL 语义骨架（UNION / 状态集合 / 索引使用）
- 时序图 + **异常路径**（正常路径 / 熔断 / 重试 / 回滚 / 跨进程）
- 并发与一致性约束汇总表
- 配置键清单（含命名风格对齐）
- Excel / MQ / 外部契约的字段清单
- 自测清单

**不写**（实现细节交 实现方 决定）：

- 完整 Java 类源码（Executor / Consumer / Service Impl 等）
- `@Annotation` 注入写法
- Lambda / Stream / BeanUtils 具体用法
- 方法内算法细节

**Why**：
- 写死代码限制 实现方 对最佳实现的判断（事务边界、工具类、分批策略）
- 方案和最终代码会双份腐烂
- 评审注意力会被语法细节吸走，错过策略层问题

**判定标准**：单份 design 超过 300 行时，先自问"是不是有大段 Java 块？"有就砍成"职责清单 + 约束表"。

但**完整性不能打折**：
- 时序图必须画异常路径 + 跨模块/跨进程调用
- Excel / 外部契约字段必须列清，不能让 实现方 猜
- 典型目标：300–600 行策略型文档 > 800+ 行代码塞入型

## 二、产出后强制 2-3 轮自审

**不要立即交付给用户或 实现方 编码**。先自审：

- **Round 1：完整性审查** — 对着目标/验收标准逐条勾，看每条都有落地路径；覆盖正常 + 异常 + 边界；**跨模块/跨进程/跨人/状态机超 3 状态的需求是否都有对应业务流单元**（见 §4.6）
- **Round 2：一致性审查** — 交叉检查 spec 约束、design 策略、接口契约、状态机、SQL 状态集合、Redis key 命名、配置项是否前后对齐；章节编号 / 交叉引用是否对；**并按 `rules/context-engineering.md §产出侧` 逐段问「删掉这句，实现方会做错什么」**——答不出的解释性段落、与别章重复的复述、装饰性括注一律删
- **Round 3：对抗性 + 风险主动暴露审查**
  - 假设自己是 实现方 / QA 去读：哪些地方写得让人会理解错？哪些策略会踩事务、并发、幂等、跨模块的坑？
  - **三视角扫描**：再切「架构师（运行时假设/分布式一致性/并发安全/降级回滚）/ 前端·UX（技术栈匹配/兼容/资源泄漏）/ DBA·运维（SQL 性能/存储安全/容量规划）」三个视角各扫一遍，对应视角的风险逐条过——比单一"实现方/QA"视角更能逼出跨域盲点
  - **主动列风险决策点表**：把"已决定 / 待用户决策 / 未决定但暂按默认"三类分开，让用户一眼挑出要改的；不要等用户追问才浮现
  - Round 3 在文档大于 300 行、或涉及新表 / 异步流程 / 跨模块时必做
  - **独立审（Round 3 必做时，交实现方编码前）**：对抗性审查交给**新上下文**的 `sa` 子代理（中档模型起；跨模块 / 状态机 >3 态才用高档），只给 design 文档 + spec + 相关代码路径，**不给作者的推理过程**；返回"会被理解错的点 / 会踩的坑 / 契约缺口"三类清单，主会话逐条裁决后改文档。作者在同一上下文里自扮 reviewer 消不掉自己的盲区（§二点一 的"评分单调上升而用户仍能找出问题"即此形态）

**应用约束**：
- 单轮生成不超过 1000 行不自审就交付
- 每轮输出明确结论：通过 / N 处问题 / 需用户澄清 X 项
- 至少 Round 2 通过再给用户看
- 用户提问"是否存在缺失、错误"时，这是 Round 3，要当对抗性审查对待
- 发现问题**先改文档再继续**，不要留到编码阶段

### 二点一、轮次防退化清单

**轮数 ≠ 质量**。用户多次让"再检查一遍"时,每一轮必须有不同的强制动作,否则会退化为复述 + 评分表演。

**退化的红旗**(出现即说明这一轮没真做):

- ❌ 给整体评分(`9.5/10` 这种没有可衡量标准的数字)
- ❌ 用"已达到 X 水平 / 可对外阅读"等空头结论代替具体证据
- ❌ 修订没有引入新证据时声称"质量提升"
- ❌ 输出结构与上一轮高度雷同(主线 OK + 几处小问题 + 评分)
- ❌ 评分单调上升(9.0 → 9.5 → 9.7)但用户每轮都能找到新问题

**每一轮的强制动作差异化**:

| 轮次 | 必跑动作 | 验证标志 |
|---|---|---|
| Round 1 完整性 | 逐条勾验收标准,每条说出落地位置 | 能列"需求→实现"对照表,而非"主线 OK" |
| Round 2 一致性 | 跨章节引用 + 字段名拼写 + 状态码 全部交叉核对 | 能命中至少 1 处不一致或确认无 |
| Round 3 对抗性 | **先写"陌生 reviewer 会问的 3 个具体问题",再回答** | 3 个问题描述具体场景,不是"是否清晰"这种空问 |

**修复后必跑的微自检**:

改了任何一处(代码 / 坐标 / 文案 / 字段名),必须:

1. 列出这一处**影响的相邻元素**(同 y 坐标范围 / 同字段消费方 / 同链路下游)
2. 逐一验证它们没被破坏
3. 才能宣告修复完成

例:加旁注 y=876,必须列 y=870-882 范围内所有元素,确认无水平重叠。

**给用户的识别信号**(用户可据此判断 Claude 退化):

- Claude 说"X 分"但拒绝列出"如果新人读到 Y 段会困惑哪一句"
- Claude 说"修订完成"但不主动列出修复影响到的其他位置
- 同一类问题第 3 次被问起还在补充新发现 → 说明前 2 次没做完

### 二点二、视觉敏感任务专用三轮(HTML / SVG / UI mockup / diagram)

针对生成视觉产物的任务,§二 通用模板做以下映射:

| 轮次 | 名称 | 强制动作 | 退化信号 |
|---|---|---|---|
| 1 | **业务自检 = 完整性 + 一致性 两份输出都要** | (a) 列"该画的元素清单"逐条对照图 (b) 图里每个字段/术语/状态码 grep 追到源码常量 | 没列清单 / 抽样核 2-3 个就说"基本对" |
| 2 | **视觉自检** | 起 playwright / chrome-devtools / headless chrome 截图 + 读图,列**截图里实际看到的具体问题**(坐标 / 区域) | 不开浏览器,继续用坐标算 |
| 3 | **修复 → 再截图** | 改完**必须再截一次图**,与第 2 轮截图对比,确认问题消除;有新问题继续修-截-验循环 | 修完只用坐标说"应该好了" |

**关键映射**:

- §二 Round 1 + Round 2(完整性 + 一致性) → **合并到本第 1 轮**(视觉产物的"源"就是业务代码,两件事一起做更高效)
- §二 Round 3 对抗性 → **被截图取代**(截图就是最硬的"陌生 reviewer 视角")
- **新增**:修-截-验闭环(单次截图不够,必须修后再截以验证)

**第 1 轮"两份输出"硬约束**:

不能"主线 OK + 几处小问题"含糊带过。必须分别给出:

1. **完整性输出**:列表形式列"该画的元素",勾选每个是否在图里
2. **一致性输出**:列表形式列"图里所有字段/术语",每一个对应到源码哪个常量/类

两份输出都缺 → 第 1 轮没做完,不能进第 2 轮。

**不适用场景**:

- 纯文档 / 纯代码任务:走 §二 原通用三轮
- 抽象 architecture 决策(无视觉产物):走 §二 原通用三轮

只有产出 HTML / SVG / mockup / diagram 等**可截图的视觉文件**时才走本节。

**Why**(本规则升级背景):

某项目时序图任务,3 轮审查 + 评分单调上升却被持续找到 bug(每一轮都说"9.X/10 可对外",但第 4 次被问到时仍有新发现);且修订时引入新视觉重叠(异常旁注与相邻 self-loop 完全水平撞行)——根因是"角色切换不彻底 / 不渲染只读源 / 评分遮羞布 / 修复时局部视野"。本子节是 §二 通用框架的**质量维度补丁**。

## 三、过度设计默认反对

设计时出现以下"为以后可能需要"的元素，先自问三个问题，不能三题全 Yes 就删：

1. 这个开关/机制上线后**一定**会被用到吗？
2. 删掉它**当前**流程会出问题吗？
3. 即使未来需要，**现在**不做会有重大代价吗？

**常见过度设计**：

- **降级开关**："万一出问题可以关" — 开关本身可能成为事故源，删
- **清理 JOB**："30/90 天后物理清理" — 软删通常够用，真需要等量积累了再补
- **预留字段**：`version / ext / reserved_1` — 改不动的时候再加列
- **扩展点**：为"未来可能"的第二个实现抽接口 — 真来了再抽
- **多层抽象**："以后可能多态" — 现在只有一个就写一个
- **冗余日志**："万一排障要看" — 关键路径打点即可，别 TRACE 级刷屏

**Why**：典型复盘中出现过「业务降级开关 + 30 天物理清理 JOB」两处过度设计，都是用户问"针对什么 / 本期需要吗"才去掉。预先自审能省这轮往返。

**How to apply**：
- 每加一个"机制/字段/开关"前，脑内跑上面三个问题
- 写进设计前，如果答不出"为什么必须有"的具体业务或故障场景，就删
- Round 3 审查时专门扫一遍文档里所有的"可选 / 预留 / 扩展 / 降级 / 后续"字样，挨个质疑

## 三点五、契约层细节必须写准（字段名 / 方法可见性 / 表名）

§一 "只写策略与契约，不写完整实现"是好原则，但**契约层的细节必须 100% 准确**——这是契约，不是实现。常见漏写导致后续返工的：

1. **字段命名表**：新增 VO / 表 / DTO 时,如果声明"参考/复用既有 X"，必须列字段命名对照表（新字段名 → 既有字段名 → 类型）。漏写一次返工字段名 + 字段访问 + 序列化口径，全链路雪崩。

2. **复用方法的可见性**：方案写"调用 XServiceImpl.doSomething(...)"时，必须先核实该方法是 `public` / `protected` / `private`。`private` 方法无法直接调用，要么提可见性（影响别人），要么复制（增加重复）——这是设计决策，不能丢给实施阶段拍脑袋。

3. **表名 / 列名拼写**：方案写 `t_xxx` 或 `xxx`，必须用 `SHOW CREATE TABLE` / mapper XML / 项目 DDL 历史比对一次，**不允许靠记忆写**。表名笔误读者会困惑，最坏情况 DDL 在错表上跑。

4. **配置键 / Redis key / 环境变量**：方案出现的所有外部标识符（含字典 entry name、JSON 路径），必须 grep 项目内既有用法验证拼写一致。

**Why**：契约层的 1 字之差 = 实施阶段 1 天返工。"先写后改"的成本远高于"先核后写"。

**How to apply**：
- design 评审时多一道"契约抽样核验"：随机抽 3-5 个新字段名 / 方法名 / 表名，逐一 grep 项目验证存在 + 拼写正确
- VO 新增方案必含"字段对照表"章节,即使只有几行
- 复用方法在方案里必须显式标注可见性 `(public)` / `(private,本期复制)` / `(private,本期提为 package-private)`

## 三点六、前后端 / 跨方契约前置对齐

方案出"新 VO 不继承既有表单基类 / 字段名 X / 类型 Y"等决策时，**必须同步问"另一方怎么发请求/接响应"**。后端单独闭门做的字段命名 90% 概率与前端口径分歧，事后必须返工。

**强制问的三个问题**（涉及新接口或新 VO 时）：
1. 前端 / 调用方此场景**复用既有页面/SDK** 还是新写？
2. 如果复用，复用源是什么？字段名口径以源为准还是新定？
3. 跨方约定的契约（字段名 / 类型 / 必填）写在哪里？方案内 or 单独契约文档？

回答不齐时,方案的 VO 设计是"未冻结"状态,实施前必须先回到 PM/SA/前端 三方对齐。

**Why**：前后端各看各的方案是经典翻车场景。典型案例：设计文档明确"不继承既有表单基类"，但前端是直接复用既有表单 VO 提交的——实施完成后才发现字段名全错位，整套 VO + Service 重构。

**How to apply**：
- PM/SA 写完方案文档,review 前必须邀请前端/调用方过一次方案
- 评审记录里显式记一句"前端/调用方此场景的复用源 = X / 不复用,新写"
- 实施期间发现方案没说清的契约细节,**先停下来对齐**,不要自顾自下定义

## 三点七、视图接口聚合（一模块一接口 / 禁前端拼装 / 后端聚合）

UI 模块（卡片 / 列表 / 总览）的**核心数据**必须由**单个接口**按原型模块对齐、一次性一致快照返回。

- **判定规则（review 门禁）**：一个 UI 模块的核心数据若需前端 **≥2 次调用**才能渲染 → 判违规，把聚合推回后端。
- **禁的是"前端拼装"，不是"后端聚合"**：✅ 允许且鼓励 Controller / BFF 在**一个接口内部** compose 多 service / 多查询，组装成视图 VO（`OverviewVO` / `ListItemVO`）一次返回；❌ 禁止前端调多 endpoint 再 merge 成一张卡；❌ 禁 N+1（列表行状态 / 详情在列表查询里一次补齐，不"列表取行 + 逐行调详情接口"前端拼）。
- ⚠️ "一个接口一块数据" ≠ "一条 SQL 喂一张卡"——别误读成单 SQL 而打巨型 join 或反范式；聚合就该落在后端这一层。
- **命名 / 契约**：接口按模块命名（`/dashboard/overview` / `/xxx/list`），返回视图 VO 不是 entity（接 §三点五 / §三点六）。
- **刻意例外（必须显式 + 留痕）**：模块内某子部分计算极重、刷新频率 / 时效明显不同（如总览挂全表统计趋势图）时，允许拆独立接口让主卡片先出——这是显式设计决策，不是前端图省事的偶发拼装；区别在"故意拆 vs 顺手拼"。

**Why**：前端多接口拼一块卡片会引入瀑布延迟、部分失败半残、时点不一致（总数与明细对不上账）、业务语义泄漏到前端四类问题；后端单接口聚合 = 一致快照 + 契约清晰 + 干掉 N+1。

## 四、测试归属表（行为单元 + 5 维打分）

SDD 完整流程的 `02-design.md`（或 design 文档对应位置）**必须**产出"测试归属表"，作为 Dev 写测试和 QA 验收的共同输入。这一节解决"哪些测自动化、哪些测人工、各走哪一层"的源头问题，避免事后再用用例文档反向倒推。

> **项目落地约束**：每个项目的 `.claude/CLAUDE.md` 必须维护一节"测试基础设施映射"，把本节的 5 个归属层级映射到项目具体落点（目录 / 命令 / 样例类 / profile / 工具链）。归属表只用层级名，**项目映射给出"怎么跑"**——这是规则可执行的前提。

### 4.1 行为单元拆解

把每条需求拆成"**输入 × 状态 → 预期输出**"的最小可断言点，每个单元一行进表。

要求：

- 一条需求通常拆出 3–8 个行为单元，跨 2–4 种测试层级
- 行为单元必须**可独立验证**：能写出明确的"成功判定标准"
- 异常路径（必填校验 / 权限拒绝 / 外部失败 / 状态非法）也是行为单元，不能只写主线
- 不写"覆盖率"目标，只问"这条需求要 work，哪些行为必须为真"

### 4.2 5 维打分（需求视角，不是用例视角）

每个行为单元按下面 5 维打分（1=低 / 2=中 / 3=高），加和得到复杂度总分：

| 维度 | 1 分 | 2 分 | 3 分 |
|------|-----|-----|-----|
| **数据准备** | 写死参数即可 | DB 造一条记录 | 需真实身份证 / 外部凭据 / 跨表数据集 |
| **外部依赖** | 无 | 单一稳定依赖（DB / Redis） | 多依赖含第三方（大数据局 / 人脸 / MQ 异步回调） |
| **状态前置** | 无前置 | 单一前置流程 | 多步前置 + 时间窗口 / 审批状态 |
| **断言复杂度** | 看返回码 / 字段值 | 看 DB 状态变更 | 看 UI 渲染 + 多表 + 文件内容 |
| **可重复性** | 幂等可重跑 | 跑完需清理 | 一次性（如签约后无法重签） |

**总分映射测试归属**：

| 总分 | 复杂度 | 归属 |
|------|--------|------|
| 5–7 | 低 | **必须自动化**：单测 / 契约测试 / 集成测试 |
| 8–11 | 中 | **应自动化但克制**：集成测试 或 E2E 黄金路径（用例数刻意限制） |
| 12–15 | 高 | **人工验证**：进提测 checklist，禁止强行自动化 |

### 4.3 测试归属表必含字段

```
| 行为单元 | 数据 | 外部 | 状态 | 断言 | 可重复 | 总分 | 归属层级 | 备注 |
```

- "归属层级" 必须是下面之一：`unit` / `contract` / `integration` / `e2e` / `manual`
- 每个 `e2e` 行为单元都要在备注里说明"为什么不能下沉到 integration"
- 每个 `manual` 行为单元都要在备注里说明"为什么不能自动化"（数据 / 外部 / 一次性）

### 4.4 何时必产出

| 流程 | 是否必产出测试归属表 |
|------|------------------|
| SDD 完整流程（新模块 / 新接口 / 跨模块） | 必产出 |
| 简化流程（单模块、小范围改动） | 不强制，但 Dev 自测时心里跑一遍 |
| 配置 / 文案 / 小修复 | 不需要 |

### 4.5 自审要点（并入 §二 Round 1/2/3）

- Round 1：每条需求的行为单元是否齐全（含异常路径 + **链路级业务流单元**，见 4.6）
- Round 2：归属层级是否与项目现有测试基础设施对齐（有没有用了项目里不存在的测试方式）
- Round 3：`manual` 行为单元的"为什么不能自动化"理由是否站得住，避免把"懒得自动化"伪装成"高复杂度"

### 4.6 业务流单元（链路级，与点级行为单元并列）

行为单元是"点"，业务流单元是"线"。两者独立存在、缺一不可。

**触发条件**：需求涉及下列任一情况，**必须**显式产出至少 1 条业务流单元：

- 跨模块协作（Controller → Service → Mapper 不算；跨 Spring Boot 模块算）
- 跨进程调用（MQ 异步、HTTP 调用第三方、定时任务、回调）
- 跨人/跨角色协作（申请人提交 → 一级审核 → 终审）
- 涉及时间窗口或状态机超过 3 个状态

**业务流单元写法**：

```
| 业务流 | 起点 → 关键节点 → 终点 | 链路断言 | 跨界数 | 数据 | 外部 | 状态 | 断言 | 可重复 | 总分 | 归属层级 | 备注 |
```

新增字段：

- **链路断言**：首尾状态 + 中间关键节点（不是单点 200，是"提交后 60 秒内 status 从 SUBMITTED → VERIFIED，且消费结果已落库"）
- **跨界数**：链路上跨了几个模块/进程边界（这是判定归属层级的关键信号）

**异步终态门禁**：

- HTTP/Dubbo 返回成功、消息发布成功、任务入队或取得 request/message ID，默认只证明 `accepted/enqueued`，不自动证明下游已处理或业务已完成。
- 设计每条异步业务流时，链路断言必须同时写明：**受理态、业务终态、终态观察点、最长等待窗口、超时/失败判定**。观察点应是回调、状态查询、消费记录、provider 记录、最终 DB 状态或等价事实源。
- 显式区分生命周期，例如 `accepted ≠ provider processed ≠ submitted/delivered/completed`；不得拿前一阶段的成功证据替代后一阶段。
- 当前系统无法观察业务终态时，必须把它列为契约缺口和风险，归入 `e2e/manual` 补证；不能把链路设计成仅断言同步返回码。

**业务流单元归属规则**：

| 跨界数 | 推荐归属 |
|------|---------|
| 0（同模块同进程） | 拆回行为单元，不算业务流 |
| 1（单跨界，如 web→mq） | `integration` |
| 2（如 web→mq→第三方） | `e2e` 黄金路径 |
| ≥3 或含真实人脸/真实证件 | `manual` |

**与点级行为单元的关系**：

- 业务流单元 ≠ 点级行为单元的简单拼接
- 业务流单元的断言**必须有点级单元覆盖不到的内容**（首尾时序、链路完整性、跨界状态一致性）
- 点级单元全绿不代表业务流单元绿（典型反例：MQ 消费成功但状态字段没更新，单元测试都过但链路断了）

**Why**：
- 现实事故 80% 出现在"单元绿但链路红"的接缝处，纯点级测试抓不到
- 把业务流显式建模到设计阶段，避免被拆散成多个独立点单元后丢失上下文
- 业务流单元天然倾向 e2e/manual，反而能让 SA 主动思考"这条链路谁来守护"

**How to apply**：
- SA 写 `02-design.md` 测试归属表时，**先列业务流单元，再拆点级行为单元**（防止拆散后忘了线）
- 一份 design 通常有 1-3 条业务流单元 + 5-15 条点级行为单元
- Round 1 自审专门扫一遍：跨模块/跨进程/跨人/状态机超 3 状态的需求，是否每条都有对应业务流单元；没有就是漏

### 4.7 e2e 子型选型（API vs UI/Playwright）

e2e 层不是同质的，必须按"是否必须走 UI 才能验证"拆成两子型：

| 子型 | 工具姿势 | 适用场景 |
|------|---------|---------|
| **API e2e** | curl / HTTP client + DB 断言 + 项目加密协议复刻 | 列表查询、状态机推进、文件导出、枚举探测、批量操作 |
| **UI e2e** | Playwright / Cypress / Selenium + page object | 弹框、字段渲染、必填校验、按钮置灰、跨页面跳转、拖拽、上传 |

**判定规则**（行为单元描述含下列关键词 → 必走 UI）：

- 弹框 / dialog / 弹层 / 抽屉
- 字段渲染 / 回显 / 选项 / 列表展示
- 必填校验 / 表单校验 / 错误提示
- 按钮置灰 / 禁用 / 显隐切换
- 跨页面跳转 / 路由切换
- 拖拽 / 上传 / 富文本

**优先 API e2e**（更稳、更快、更省）：

- 列表查询 / 筛选 / 分页 → curl + db 断言
- 状态机推进 → API 触发 + db 轮询
- 文件导出 → curl 下载 + 文件断言
- 枚举字典探测 → curl + JSON 断言
- 批量操作 → curl 提交 + db 校验

**UI e2e 用例数硬约束**：每个项目控制在 **3-5 条黄金路径**，禁止扩展到全量用例。每加一条 UI e2e 用例先回答："如果不加，业务流断了能在哪一层捕获？"——能在 API e2e / integration 捕获的就不要 UI e2e。

**Why**：UI e2e 维护×执行×排障成本是 API e2e 的 5-10 倍。不限制就会重蹈"用例文档驱动"的覆辙——红得没人信，最后全员忽略。

### 4.7.1 e2e 三层流转门禁（探索 → UI → API+DB，严格先后，禁跳层）

沉淀一个新业务流的 e2e 时，三层有**强制流转顺序**，不是并行/任选：

| 顺序 | 层 | 做什么 | 门禁 |
|------|----|--------|------|
| **1** | **① 探索** | 摸清真实页面/交互/数据现状（能进页、能渲染、端点契约、数据现状全跑通） | **完全通过**才往下 |
| **2** | **② UI e2e（主线）** | 真实浏览器业务流驱动 + 渲染断言（Playwright real 模式注入 token） | 主线验证，跑绿才进 ③ |
| **3** | **③ API+DB（最后兜底）** | API 直连 + DB 交叉核验，只补 **UI 够不到** 的精确落库/边界/回归 | 放最后 |

**❌ 硬禁止"直接处理 API"先做 ③**。③ 不是"先行主力"，是最后兜底层。

**Why**：
- 先 ③ API+DB 会绕过"前端真实怎么用"的视角，丢失契约消费层的真实问题——用精确 id 直连后端碰不到前端按名字/页面选择时的坑。典型事故：某详情链路**UI 层才暴露同名相似项陷阱**（按名称子串匹配撞到另一条名称包含它的记录），纯 API 直连用精确 id 永远碰不到。
- UI 先行能在写后端兜底测试前就发现前端契约/渲染/数据现状问题，避免在错前提上写一堆 API 断言。

**How to apply**：
- 新业务流：**先 ① 探索跑通 → 再 ② 写 UI driver 跑绿 → 最后 ③ 补 API+DB 兜底**。不要一上来写 pytest case 戳后端。
- 已绿的反序产物不必返工，但顺序认知按此纠正，后续严格 ①→②→③。


### 4.8 测试数据策略分层

| 归属层 | 数据来源 | 准备方式 | 关键约束 |
|------|---------|---------|---------|
| **unit** | 内存 mock | 写死参数 | 不连任何外部 |
| **contract** | MockMvc 内嵌假 JSON | 不连任何外部 | 只验 HTTP 边界 |
| **integration** | dev DB 临时记录 | 跑完清理 | **状态字段变更边界见 `refs/test-suite-hygiene.md §九第 4 条`** |
| **e2e (API/UI)** | 真实数据反推 | 从 DB 查可用数据 + 项目加密协议复刻 | 不接受 mock 外部依赖 |
| **manual** | 测试环境真实凭据 | 不可重复 | 只跑一次，证据随提测材料留存 |

**核心硬约束**：

1. **状态字段变更边界**：详见 `refs/test-suite-hygiene.md §九第 4 条`——允许直接把业务状态字段更新到所需状态以跨过**本批次不验证**的前置环节，但禁止对**本批次正在验证的行为本身**直接改状态，且须遵守其流程顺序与 `§十` 六步留痕协议。无法获得真实前置数据、又不属于可跳过前置范围时，只能标 `blocked:data`。
2. **核验类测试必须用真实数据反推**：涉及外部核验（如身份证查户籍、人脸活体、合同签署），必须从生产/测试环境真实数据反推可用样本，不接受 mock 外部依赖的响应。
3. **数据准备成本进 5 维打分**：数据准备越复杂，5 维总分越高，越倾向 manual——这是设计阶段就应预判的复杂度信号。

**Why**：测试数据是测试可信度的根基。改状态字段一时方便，但下次同链路真有 bug 时谁也不信测试，整个套件失去守护意义。

**Why**：
- 用例文档是 QA 历史产物，按手工测试视角拆，做自动化会被错前提绑架
- 从需求拆行为单元，能让 SDD 阶段就定下测试归属，开发和测试同步推进，不再"先开发完再想怎么测"
- 5 维打分客观化"复杂度"，避免研发和 QA 对"该不该自动化"扯皮
- 高复杂度强制人工，反而提升自动化套件信任度（红了就是真 bug）

**How to apply**：
- SA 写 `02-design.md` 时把测试归属表当成必含章节，与 DDL / 接口契约 / 状态机同级
- Dev 按归属层级写代码同步写测试（unit/contract/integration 在 Dev 职责内）
- QA 按归属表做本地自测覆盖说明，`manual` 行为单元交提测 checklist
- 行为单元发生增减时同步更新表，不允许代码和归属表脱钩

## 五、代码结构按业务域规划（多模块 / 域级）


域级 / 多模块项目，`02-design` 必须把**包结构**作为设计决策写明（别等编码完才发现小功能模块全平铺在根包）。综合 by-feature / DDD bounded-context / Spring Modulith / package-by-component / screaming architecture：

1. **顶层包按业务域 / 能力命名，禁技术分层做顶层**（强共识）：`<域A>/ <域B>/ common/`，**不要** `controller/ service/ dao/ entity/` 当顶层。验收标准（screaming）：**陌生人扫顶层包能说出"这是什么系统"**，而非"用了什么框架"。
2. **域内对外只暴露声明的 API、实现 package-private；跨域只经对方 API，禁深引内部包**（强共识、可机械强制）：封装优先靠**编译器 package-private**（零成本），不靠 code review 盯。
3. **域间依赖单向无环（DAG）**（强共识、可机械强制）：循环依赖一律拒；依赖关系可显式白名单。
4. **`common` / 共享内核只放接口·契约·纯工具，且不反向依赖任何业务域**（强共识）：防"共享包变垃圾场" + 隐式耦合。
5. **机械强制 > 约定**（对齐 §三点五 + `refs/engineering-tradeoff.md`）：上面 2 / 3 用 **ArchUnit**（`slices().should().beFreeOfCycles()` / 内部包访问规则）或 **Spring Modulith** `ApplicationModules.of(App).verify()` 做 **CI 单测门禁**，违反即红——别让"按域分包"沦为靠自觉的摆设。

**判据（防过度分包，YAGNI）**：单一业务域 + 术语统一 + 小项目 → flat / by-feature 够用，**别预先按域深嵌**；命中任一才必须按域分组——多业务域且术语跨域语义不同 / 小模块已平铺根包且在增长 / 多人按域 owner / 需保留"抽微服务"迁移路径。

**不硬性规定（留给域复杂度判断）**：域内是否再上 hexagonal / ports-adapters 分层、是否为低耦合接受切片间适度重复（VSA）——这些是更细的设计取舍，按域复杂度定，本条不强制。

**Why**：小功能模块平铺根包初期省事，但模块一多就找不到边界、无法按域 owner、加新特性要散改多处；"按域分包 + 编译器/ArchUnit 守边界"把结构变成可演进资产。典型教训：某后端的同步 / 现场 / 补录 / 记录等小模块曾平铺根包，后来需专门重构按域归组。
