# Lifecycle Gates Design

本文定义「需求 → 开发 → 测试 → 验收」全链路的阶段门引导。目标：任何人装了工具，每个任务在阶段交接处都有出口检查，而不只是知道下一步做什么。

## 问题

1. `sdd-pipeline` 的四道门只被 `add-module` / `auto-sdd` 引用；一句话开干、小改、轻量任务没有任何门。
2. `flow` 只按产物文件是否存在判阶段，不核对出口判据，是地图不是关卡。

## 设计原则

- **不复制判据**：门的判据只在 `sdd-pipeline` 写一份，`flow` 按门编号引用。
- **按任务规模分档**：小任务过轻量检查，不被流程拖慢。
- **不依赖任何本机设施**：本组件随工具分发，门的检查只读仓库内的产物、git 状态与测试证据，不调用也不假设存在外部台账或脚本。

## 一、阶段门与规模分档

出口检查对齐 `sdd-pipeline`：

| 交接点 | 对应门 | 出口检查 | 证据 |
|---|---|---|---|
| 需求 → 开发 | 门1 需求冻结 | 验收条件可判定（EARS 句式或 Given-When-Then），影响范围已列，歧义已澄清 | 需求卡或需求简报 |
| 开发 → 测试 | 门2 设计/编码 | 契约已冻结；主会话 diff 自审有结论 | 自审结论 |
| 测试 → 验收 | 门3 QA 证据 | 每条验收条件有执行证据，PASS 也留证据；证据不足只能 BLOCKED | 测试报告 / 原始输出 |
| 验收 → 交付 | 门4 验收判据 | 需求全覆盖、QA 证据齐、审查判档完成（e2e 沉淀按项目要求） | 覆盖矩阵 + 判档结论 |

规模分档（`flow` 读取任务已有的分档结果，不自行判档；没有分档信息时按「完整流程」提示，由使用者降档）：

| 档 | 过哪些门 | 备注 |
|---|---|---|
| 小改（文档/配置/≤5 行零风险） | 仅门2 自审 | 门3 以一次实际运行或检查代替 |
| 轻改（单模块、无高风险信号） | 门1 轻量（需求卡含验收条件）+ 门2 + 门3 | 门4 合并进收口汇报 |
| 中改 / 完整流程 | 门1–门4 全过 | 完整流程由 `add-module` / `auto-sdd` 驱动，本身已含四门 |

## 二、`flow` 的改造

- 阶段表增加「出口门」「证据」两列，引用上表的门编号；完成判据以门判据为准。
- 输出在阶段条之外增加一行「门状态」：每个已走到的门标 `通过 / 未过 / 未记录`。`未记录` 单独列，不等同于通过。
- `flow` 仍然只读、不执行。门是否通过，依据产物、git 状态与测试证据判断，缺证据就如实标 `未记录`。
- 进入某阶段前，上一阶段的出口门未过时，建议下一步是「补齐该门证据」而非继续往下走。

## 三、范围

本次实现：

1. `flow` 阶段表加门列与门状态输出。
2. `sdd-pipeline` 的引用关系补一条指向 `flow`。
3. `USAGE.md` Quick Start 补一句门与分档的说明。
4. 对应的 skill 内容测试（门列、门状态三值、未记录不等同通过、不引用外部台账）。

不在本次范围：

- 任务效率的记录与统计（属于工具维护者的本机度量，不随组件分发）。
- `status.json` 式阶段状态文件。
- 返工原因的自动分类。

## 四、风险

| 风险 | 处理 |
|---|---|
| `flow` 靠读产物判门，粒度粗 | 缺证据标 `未记录`，不假装通过；证据来源只列仓库内可核对的产物 |
| 分档信息缺失导致小任务被强拉全流程 | 无分档信息时提示可降档，保持「不得强拉完整流程」的既有约束 |

## 五、验证

- skill 内容测试：断言门列、三种门状态、`未记录` 语义、无外部台账引用。
- 安装：临时 home 安装后 `flow` 内容就位，doctor 通过，卸载后移除。
- 全量：`pytest`、`sanitize_check`、`template_integrity_check`、`context_budget_check`。
